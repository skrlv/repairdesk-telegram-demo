# Устройство проекта

`Telegram Update → BotService → SQLite (заявка + история + outbox) → локальный sink или TelegramClient`.

Клиент определяется по Telegram from.id в личном чате, сотрудник — по STAFF_IDS. Все чтения карточки/истории ограничены владельцем или сотрудником. Чужой и отсутствующий номер дают одинаковый отказ; чужое фото не отправляется. SQL параметризован. Стенд заменяет доверенный Telegram transport учебными актёрами и позволяет менять роль для показа; публиковать его как общедоступную админку нельзя.

Шаги: `device → description → photo → consent → contact (при согласии) → confirm → ticket`. Фото и телефон можно пропустить; устройство/описание обязательны. `/new` не затирает черновик. Кнопки согласия, подтверждения и отмены связаны со случайным nonce черновика. Старая кнопка не действует на новую заявку. Черновик переживает перезапуск.

Статусы: `new → diagnostics → in_progress → ready → closed`. Из `new`, `diagnostics`, `in_progress` допустим `cancelled`. Из `closed`/`cancelled` переходов нет. Callback статуса содержит ожидаемый исходный статус; устаревший отклоняется. История хранит UTC, actor ID и переход. Длинные ответы делятся с учётом UTF-16 лимита.

Таблицы: sessions, tickets, history, processed_updates, polling_cursor, outbox. В стенде добавляется demo_messages. Вложения — только file_id; demo-photo является учебным идентификатором. В журнале входящих updates сохраняются ID/время, без исходного тела. Исходящие ответы могут содержать описание и телефон сотруднику, поэтому защита нужна для всей базы и её копий.

Нагрузочные, эксплуатационные, настоящие сетевые и юридические проверки не выполнялись. Это однопроцессный демонстрационный проект. Несколько runner требуют отдельного механизма владения очередью. SQLite защищается правами файловой системы, шифрование приложением не реализовано.
